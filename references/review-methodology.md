# Review Methodology

Claude performs the review natively using its own tools. No subprocess AI.

## Severity
- **CRITICAL** — security hole, data loss, crash, or broken core flow.
- **MAJOR** — incorrect behavior, missing auth/validation, significant perf regression.
- **MINOR** — bugs in edge cases, smells, missing tests for new logic.
- **INFO** — style/nits, optional improvements.

### Impact floor and axis rule
1. Rate every finding on each impact axis (Security, Data integrity, Functional, UX, Performance) and take the MAX (pointer: `verification-pitfalls.md` #27).
2. A finding that defeats the PR's own stated guarantee (the vuln it claims to close, the "no double charge" it claims to fix, the "sanitized" it claims to deliver) is at least MAJOR, whatever the actor gating (pointer: pitfall #25).
3. Actor gating ("contributor-only", "dev-gated", "admin-only"), timing ("edge", ">N seconds"), and "runtime-unverified" lower LIKELIHOOD. They never lower severity below the impact floor. A likelihood claim of "edge" must be measured or reproduced before it is used (pitfall #32).
4. A "closed / fixed / refactor-only" claim is rated with the same evidence bar as an open finding (pointer: pitfall #26).

## Detection-trace rule
Every finding MUST state HOW it was found — e.g. "traced `$_POST['key']` from `handle()` into `$wpdb->query()` with no `prepare()`". A finding without a concrete trace is not reportable.

## Line-number rule
Cite line numbers ONLY from Read tool output (it shows real line numbers). Never infer line numbers from diff hunks or from memory — re-Read the file at the cited line before reporting.

- Take the number from the file at the reviewed head (`grep -n` or a Read of that file), never from a diff hunk header, a `sed -n` / offset listing you count by hand, or a subagent's summary.
- Every finding carries an `anchor`: a fragment of the code copied from its cited line. The renderer refuses the report when the anchor is not on `line`..`end_line` and says where it actually is.
- Write citations with the repo-relative path (`src/Checkout/Order.php:229`, not `Order.php:229`): a bare filename is refused as ambiguous when two files in the checkout share it.
- Every `path:N` / `path:N-M` in the text (questions, summary, notes) must resolve to a file in the checkout with that many lines; write a line on another ref as `path@<ref>:N`. After rendering, read the citation listing it prints and confirm each cited line shows what the sentence claims.

## Skip generated/vendored files
Do not review: `vendor/`, `node_modules/`, `composer.lock`, `package-lock.json`, `*.min.js`, `*.min.css`, source maps, and build/dist artifacts. Mention them only if changing them is the PR's purpose — OR (exception) if a lockfile (`package-lock.json`, `composer.lock`) shows churn with NO corresponding manifest change, flag it as an INFO **unexplained-file** finding per `verification-pitfalls.md` #15 rather than silently skipping.

## Workflow
An optional `fresh` modifier (in the PR input, or a request for a "fresh review") forces a from-scratch review. **Fresh is a HARD reset of prior-round knowledge from EVERY source — not merely a skip of step 8:**

- **Allowed inputs in fresh mode = PR data + source code ONLY.** The only inputs are the PR metadata/comments/CI from `collect_pr.py` (or GitHub) and the source tree at HEAD. Do NOT open any local `.pr-reviews/<repo>/<pr>*/review.md` file — not to skim, not to "check what changed." The local review files are off-limits in fresh mode.
- **Do not draw on prior-round knowledge from any other source either:** prior review notes / progress logs, an earlier session, or your own recollection of having reviewed this PR before.
- **State every finding in the present tense, as a first observation.** Never frame anything relative to a prior round — no "cleared", "fixed since", "still persists", "previously found", "regression", "as before", or "round N". If the code is correct, it is simply a non-finding, not a "resolved" issue.
- **Skip step 8** and **omit the Previous-review-delta section** from the report.
- **Fresh resets prior-ROUND knowledge only.** The team standards cache (`.pr-reviews/.standards/<team>/standards.md`) is **standing** skill **config**, not a prior-round input — it is **loaded normally** in fresh mode (a different path from the per-PR `.pr-reviews/<repo>/<pr>*` review files, which ARE off-limits).
- **The test:** a fresh review must read identically whether or not prior rounds exist. If your wording would change because you happen to know the history, you are not doing a fresh review.

1. **Explore** — obtain the hunk-level diff via `gh pr diff <N>` (PRIMARY, fork-safe) or `git diff origin/<base>...<local-branch>` (the local branch created for review), then read the diff and the surrounding code with Read/Grep/Glob/Bash until you understand the change in context. Don't review from the diff alone. Scope findings to changed / newly-reachable lines — flag pre-existing untouched code ONLY when the PR makes it newly reachable.
2. **Use the PR context** — factor in the collected CI status (failing checks are findings) and the existing comments/review threads: suppress a discussion-raised issue ONLY if you have verified it is fixed in HEAD with explicit `file:line` evidence; otherwise keep it as a finding (or Runtime-unverified if the fix is unverifiable locally). A thread marked resolved is a hypothesis — verify before suppressing. Note unresolved threads that deserve attention.
   **HARD RULE: dedupe against the PR before you stage or post.** Check every finding against what is already on the PR, so we never post a duplicate.
   - **Fetch all of it.** The step 1 `collect_pr.py` output already holds inline review threads with every reply (`review_threads[].comments`), review bodies (`reviews`) and conversation comments (`comments`); use it rather than fetching again. Run `gh api` only for what it lacks, such as a linked follow-up issue or PR. Take every author: humans, bots (CI, AI reviewers) and our own prior rounds. Include resolved and outdated threads. Also open each follow-up issue or PR that a comment or the PR body points at.
   - **Classify each finding** against that set. Judge meaning, not only wording. A paraphrase, or the same root cause on another line, counts.
     - **DUPLICATE** (same point already made): drop it. If it must stay visible, rewrite it as a one-line reference with a link to the existing thread.
     - **OVERLAP** (partly covered): keep only the new part and link the existing thread.
     - **TRACKED** (a follow-up issue or PR already covers it): one-line reference to that issue, or drop it.
     - **NEW**: keep it.
   - **Record it** per finding in the findings JSON: `"dedupe": {"status": "new"|"reference"|"dropped", "url": "...", "note": "..."}`. `new` = NEW; `reference` = a DUPLICATE, OVERLAP or TRACKED finding kept as a link or a reduced comment; `dropped` = removed. `url` and `note` are required for `reference` and `dropped`.
   - **Run the gate** before staging or posting: `python3 scripts/dedupe_check.py <findings.json>` (exit 0 = clean, exit 3 = unacknowledged candidates, exit 2 = load/fetch error; `--json OUT` writes the report). It reads the three comment endpoints read-only and matches same-path lines within `--window` (default 5) and token-similar wording (`--threshold`, default 0.35).
   - **Gate before staging or posting:** every finding carries a `dedupe` tag (`new`, `reference` or `dropped`). List the candidates — findings whose `file:line` or wording matches an existing comment — and confirm each one is tagged `reference` or `dropped` with its `url` and `note`, or deliberately kept `new` with a note on why it differs. Do not stage while any candidate is unacknowledged. A location/wording match does not catch paraphrases or the same root cause on another line, so the semantic check above is still required.
   - **Re-review rounds:** a finding you raised in a prior round that is still open is NOT a new inline comment. Put it in the re-review reply flow or the persisting section. Never post it again as a fresh comment.
3. **Self-question** — before decomposing, generate AND answer a focused question set about THIS PR. Questions seed detection traces and surface unverifiable items; they are not busywork. **Bosu gate:** every question must end in a defect/validation/design check or a concrete unverified item — drop any pure clarifying or praise question that carries no defect payload (turn intent questions into defect hunts, e.g. "…and does the diff actually achieve that, or is there a gap?"). The bank is organized on a 2-phase orient→analyze skeleton; treat that skeleton as organizational only.

   **A. Orientation (always):**
   - What does the PR *claim* to do (title/body/linked issue) vs what the diff *actually* changes? Any diff file not explained by the stated purpose?
   - Why was this change made / what instigated it — and does the diff fully achieve that, or is there a gap?
   - What does it depend on *outside the diff* (callers, hooks, framework APIs, config, other plugins, DB schema)?
   - Blast radius — what breaks if this is wrong?

   **B. Scenario probes (always):**
   - Which config/path/role makes this break? (logged-out vs in; single vs multi-gateway; JS on/off; multisite; lite vs pro)
   - Worst case if the author's key assumption is wrong?
   - Unhappy path — error, empty, null, concurrent, repeated, out-of-order?
   - **Data-flow trace:** for each new input, trace **source → processing → sink** — is it validated/escaped at every trust-boundary crossing?
   - **Input → sink matrix (required whenever the diff adds or touches a request input).** Enumerate EVERY key the request can carry to the changed code: superglobals (`$_GET`/`$_POST`/`$_REQUEST`, including array-shaped values), REST params (validate_callback AND sanitize_callback AND how the controller reads it), args of custom `admin_post_*`/`wp_ajax_*` handlers and router-dispatched prefixed actions, filter/hook args, block context. For each key list the sink(s) it reaches (DB write column, echo/attr/style/script, redirect, gateway call). A key with no guard on its row is a finding candidate. Enumerate not only the keys PRESENT but the ABSENT/default/no-key path for each changed input — what each sink receives when the key is missing, empty, or left at its default — and confirm that path fails closed. The matrix is pasted into the report's Compliance trace (see `output-format.md`). N/A only when the diff adds no input, and say so.
   - **Stored-value → consumer matrix (required whenever the diff writes, persists, or filters a value).** For every value the PR stores (option, meta, session, transient, column) or emits through a new `apply_filters()`, list EVERY reader: render paths, exports, mailers, cron, other admin views, REST. Rate on the worst consumer, not the one the PR touched. Include the malformed shape (non-array filter return, empty, array-typed) for each consumer.

   **C. Dimension probes (diff-scoped, but MANDATORY when the dimension is touched — see Scaling).** Question stems; the WP mechanics + bug history live in the cross-referenced refs — do not restate them:
   - *Correctness:* intent match; edge cases; off-by-one/null/empty; concurrency/races?
   - *Security/authz:* new request path — server-side cap + nonce + ownership? IDOR? default-deny? A new or handled custom action (`admin_post_*`/`wp_ajax_*`, or a prefixed action an `init`-dispatched router fires from a request parameter) is a request-callable endpoint, possibly unauthenticated — never treat one as "internal-only" *(see `verification-pitfalls.md` #2 outer-layer, #16 single-path reachability, #17 idempotent-nonce, #19 request-dispatched action = request-callable; `known-bug-patterns.md` → Authorization and nonces: "Verify a nonce in every state-changing AJAX and admin handler", "Apply capability checks on every path, not only when a flag is passed", "Enforce the same guard on every path to the same operation or resource", "Guard handlers on prefixed hooks that request routers can fire")*
   - *Security-HARDENING PRs (a PR whose PURPOSE is to close a vuln — "Guard/Require/Sanitize/Scope/Sign/Hold-to-boundary…"):* verify the fix is COMPLETE and FAILS CLOSED, and hunt the sibling path it forgot — **MANDATORY read `references/security-hardening-checklist.md`** (per-class checklists: public-read disclosure, signed-token/fail-open, request-supplied-ID/IDOR, path-traversal, result-scoping; + the cross-cutting "enumerate every entry point to the same data — the page-load preload of an AJAX-scoped widget is the classic miss" rule).
   - *Payment / subscription state-transition PRs (a diff that touches a gateway call, a charge amount, a subscription status or expiration write, a renewal/reactivation/cancel path, or a flag that gates any of those):* build the **flag set/clear/read matrix**: for every state flag or meta the code reads to decide whether to charge, credit, or skip (an unpaid/payment-failed flag, a renewal-due or cancel-by timestamp, lock keys, idempotency keys), list every path that SETS it, every path that CLEARS it, and every path that READS it, across ALL mutating entry points: synchronous checkout, update-payment-method, gateway webhooks (invoice paid / payment failed / subscription updated), admin manual actions, cron/Action Scheduler, CLI. A payment-collecting path that does not clear a charge-gating flag (directly, OR via a shared clearer every payment path provably routes through) is a finding. Then ask: reactivation inside an already-paid period (does the code check `expiration > now` before charging?); double credit when both a webhook and a synchronous handler complete; retry of a failed gateway call without an idempotency key or a check for an already-succeeded intent; amount derived from a gross/tax-inclusive value; proration or credit read from a stored amount that the PR no longer recomputes. **MANDATORY read** the `known-bug-patterns.md` sections "Payments and subscriptions" and "State, locks and background jobs". Live-reproduce at least one path with the local gateway sandbox where bucket C consent allows.
   - *Input/output:* untrusted input validated server-side? escaped at sink? *(see `verification-pitfalls.md` "first-party values are not attacker-controlled"; `known-bug-patterns.md`: "Guard PHP 8 type-strict functions against null, arrays and false", "Cast API and database values to the documented type before strict comparison", "Resolve table names through the prefix-aware accessor")*
   - *Tests:* would the test fail if the code broke? meaningful assertions? deep paths or just the happy path? New test file: does the suite's `phpunit.xml` pattern actually collect it (the attribute is `prefix=`/`suffix=` on `<directory>`, not a glob — e.g. `<directory prefix="tests-">`; varies per plugin)? An uncollected test passes CI by never running. *(see `known-bug-patterns.md`: "Confirm a new test file is actually collected by the test runner")*
   - *Concurrency/config branches:* *(see the "config-dependent behavior" rule below + `verification-pitfalls.md` #18 runtime hook ordering; `known-bug-patterns.md`: "Scope output-suppression filters to the configuration that needs them")*
   - **Domain-sourced (NOT from the cited research — from this skill's refs + WordPress plugin domain):**
     - *Performance:* N+1, unbounded query, missing index, full scan on large installs *(see `known-bug-patterns.md`: "Index the columns large-table queries filter, join and sort on", "Keep model constructors free of eager queries")*
     - *Data/migration:* schema change reversible/guarded? cache invalidation? transaction atomicity? *(see `known-bug-patterns.md`: "Invalidate every cache key and group a write affects, on every write path", "Lock DB upgrade routines that run DDL", "Delete or update dependent records with their parent")*
     - *API/compat:* contract/signature change backward compatible? deprecations migrated?
     - *Ops:* build/deploy reproducible? committed artifacts intended? feature-flag/rollout gated?

   **Detection techniques:**
   - Perf/N+1: `grep -rn` query calls (`get_results`/`get_var`/`->get(`/`new WP_Query`) inside `foreach`/`while` bodies; flag unbounded queries (no `LIMIT`/`number`).
   - Migration: `git diff` the `db_version`/`*_version` option + upgrade routine; confirm schema change guarded + reversible.
   - Concurrency: read-modify-write without lock/atomic → flag missing compare-and-swap (`UPDATE … WHERE col = <expected>`) / transient races.

   **D. WP operationalization** — pointer only: apply the mechanics already documented in `references/standards-capture.md` + `references/known-bug-patterns.md` (nonces, `current_user_can`, `$wpdb->prepare`, `<next-version>`, custom-table cache, hook priority). DB least-privilege is **N/A** under WP's single-`$wpdb`-credential model — note it, do not ask it.

   **Scaling rule.** A+B run once on every review regardless of size. C depth is risk-/diff-scoped — EXCEPT a **mandatory deep-class trigger**: if the diff touches an **input source, an auth/permission path, a DB query, output rendering, or a state transition**, the matching C dimension is **required regardless of PR size**.
   - **Small/mechanical PR:** A + B, plus any C dimension the mandatory trigger fires.
   - **Standard PR:** A + B + the C dimensions the diff touches.
   - **Large/decomposed PR:** A + B once after PR context; the C set runs **per part** during/after decompose.
4. **Decompose** — if the PR touches many files/areas, split into logical parts (architecture, security, data layer, admin/UI, frontend, tests). Small PRs are one part.
   - **Large PRs (>15 changed files):** split into parts of ≤15 files each and dispatch one subagent (Task tool) per part with a scoped file list + the team standards. Each subagent MUST run the pitfalls list and emit a per-finding verdict (confirmed / partially valid / false positive) before returning. Each subagent MUST also surface any documented author intent in its detection trace so the central pass can weigh it. Each decomposed subagent MUST return, for every finding, the docblock/inline comment at & around the cited file:line (or an explicit "none") — the central reviewer needs documented intent to rate severity and cannot recover it after the handoff. YOU then run the two-pass verification centrally over all returned findings, adding an explicit **cross-part interaction sweep** to catch data/auth/state flow spanning multiple parts (e.g. auth logic in part A and permission check in part B). This avoids exhausting a single context on a 100+ file PR.
5. **Review each part** against: correctness, security, performance, testing, the loaded team standards (`.pr-reviews/.standards/<team>/standards.md`), AND the historical bug patterns (`known-bug-patterns.md`) — check whether the changed code repeats a pattern that has shipped a real bug before. Run `python3 scripts/scan_diff.py --pr <ref> --repo-root <checkout> [--json]` first: it greps the added lines for the mechanical "Detect by" shapes (handlers without nonce/capability, SQL outside `prepare()`, raw request input, unescaped echo, redirect without `exit`, queries in loops, …) and lists each lead with the related pattern headings. A lead is a line to read, not a finding; the judgement-based checks still need the full read. When a finding matches a historical pattern, search for precedent (`gh issue list --repo <owner>/<repo> --search "<keywords>" --state all`) and cite the closed issue in the finding. Record findings with severity, `file:line`, detection trace, and a concrete suggestion.
6. **Two-pass verification (default on)** — for EVERY finding, independently re-read the cited code and classify:
   - **confirmed** — exists exactly as described.
   - **partially valid** — exists with caveats (wrong severity, mitigated elsewhere). Adjust severity.
   - **false positive** — claim is wrong; drop it (or downgrade to INFO with a strike note).
   
   With no findings there is nothing to verify: skip the subagent and record `pitfalls checked per finding: none (no findings)`.

   **Verification subagent (mandatory):** the verify pass runs in a fresh (clean-context) subagent fed ONLY the finding verdict + the cited `file:line` + the `verification-pitfalls.md` file — NOT the original detection reasoning, PR context, or detection trace. This clean-context isolation breaks confirmation bias.

   Verification rigor (mandatory, applies to every finding regardless of severity):
   - **Trace, don't assume** — never write "likely / probably / should handle" about any code. Read it and cite `file:line`, or mark the claim unverified.
   - **Check outer layers** — before confirming "missing auth/validation/sanitization/escaping", check routers, middleware, hooks, config files, and parent callers; the protection may live in the call chain, not the handler.
   - **Check git history** — `git log` the flagged code. A deliberately introduced pattern (the commit explains why) must be rated by impact, not intent. If the documented-deliberate pattern is harmful to the system (e.g. disabled security check with a stored comment), rate it MAJOR or CRITICAL; if benign (e.g. intentional temporary shortcut with plans to refactor), rate it INFO or MINOR. Always record the commit message and author comment in the finding + Suggestion. Examples: disabling CSRF validation despite documentation is MAJOR by impact; disabling a syntax check for a planned v2 rewrite is INFO by impact. Also run `git log -p` on every guard the PR touches or weakens (capability string, nonce check, status allowlist). A guard raised in one commit and reverted in a later one within the PR is a deliberate scope decision: surface it as an OPEN finding with both commit hashes, never as a closure (Real miss: a manage-level capability raised then reverted to a view-level one; the review lane declared the vector CLOSED).
   - **Read the comments** — before finalizing any finding, read the docblock and inline comments at/around the cited `file:line`. If the author documented the behavior as intentional, cite the comment in your finding and apply the git-history rule above. Additionally, when a finding's severity depends on a security or behavioral direction (stricter vs weaker, more vs less permissive), state the direction explicitly and verify it against the code before confirming. **BLOCKING GATE:** a finding may NOT be rated CRITICAL or MAJOR until its "Documented intent" line is filled (a quoted comment or an explicit "none checked at file:line"). This is verified by the output-format Pre-emit compliance check.
   - **Search standards upward** — coding standards may live at the monorepo root (`CLAUDE.md`, `phpcs.xml`, `.eslintrc*`, `CONTRIBUTING.md`), not in the plugin dir. Cite file path + line when invoking a standard; never cite a standard you haven't located.
   - **Check the pitfalls list** — `verification-pitfalls.md` catalogs the numbered pitfall patterns (see the version line at the top of that file) (false-positive plus under-flag) and the severity-calibration themes mined from past verified findings and transcript history. Run every finding (especially MAJOR/CRITICAL) against it before confirming.
   - **Trace every input source** — a function guarded on one path may be wide open on another. Before concluding a function is "editor-only / admin-only / unreachable," enumerate ALL its inputs (`$_GET`/`$_POST`/`$_REQUEST`, REST params, block context, hook args, filters) and confirm the guard fires on EACH. A capability check inside an `if ( $capability_arg )` block does nothing for callers that pass no capability arg. (Real miss: `Utility::is_block_editor()` was rated editor-only from its block-context branch while its `$_GET['myplugin_is_block_editor']` branch rendered a fake guest cart to anonymous front-end visitors.)
   - **Separate CSRF from authorization.** A nonce (per-object or not) proves the request came from a page the user loaded; it never upgrades a broad capability into object-level authorization. When a PR binds a nonce to an object id, still ask: which capability gates the WRITE, and can a holder of that capability name ANY object id? Pointer: `security-hardening-checklist.md` cross-cutting rule.
   - **Compare against the framework's canonical implementation** — for framework-heavy PRs (Gutenberg blocks, REST controllers, WP-CLI, React/Redux), open the framework's own reference code and compare. It surfaces omitted standard mechanisms (e.g. a Gutenberg block `deprecated` entry missing the `migrate` core always ships → silent attribute loss) AND prevents false positives (e.g. `supports.innerBlocks` is not a valid `block.json` key; a runtime `BlockContextProvider` with no `providesContext` is the standard `core/post-template` pattern, not a defect). Cite the framework `file:line` you compared against.
   - **Identify config-dependent behavior** — when changed code branches on configuration (single vs multiple gateways, taxes on/off, JS enabled/disabled, pro vs lite, multisite), each branch is a distinct path. A finding can be benign in one config and a blocker in another. Flag every config-dependent path, rate severity at its WORST reachable config, and name the config in the finding. (Real miss: a purchase-button suppression filter was harmless on multi-gateway stores but emptied the only buy button on single-gateway stores — caught only by running e2e under a single gateway.)
7. **Run the author's test steps** — if the PR body carries "Review/Testing Instructions" / "How to test" (collected by `collect_pr.py` into `test_steps`: `{heading, steps}`, both empty when the body has no test section, in which case look for an ordered list of imperative steps yourself), take them, judge which are runnable in THIS local workspace, run the feasible non-destructive ones, and fold the results into the report: one `report.test_steps` entry per author step (or group of steps) with its status (`passed` / `failed` with the `finding` id / `not_run`) and a note. The renderer requires every collected step to be accounted for and fills in the author's wording itself. This runs AFTER two-pass verification (so a run can confirm/refute already-written findings) and BEFORE manual-scenario derivation (so confirmed paths drop out and refuted ones sharpen). It does not "feed" scenarios; it revises Runtime-unverified (post-hoc promotion) and annotates scenarios.

   **No documented steps?** Skip the step, note `No documented test steps.` (one line). If the team standards require testing instructions on every PR, also emit an INFO process finding (INFO never blocks Approve). Instructions present → always classify; run A (and B when the env is ready) automatically; C only on per-mutation consent; D documented.

   **HARD RULE: untested is our problem, never the author's.** A posted review (inline comments, review body, summary) never says we could not test, run or check something. When a test or check is blocked (a download returns 403, a plugin is missing, no site is up, a CI token is missing), unblock it before you give up:
   1. Use a local checkout copy or a detached worktree (for example a local copy of a required add-on under `wp-content/plugins/`), the e2e Docker site, or a live drive.
   2. Never `composer install` inside a plugin checkout. Never change a live checkout's branch.
   3. If it still cannot run, leave it out of everything that gets posted (no "not tested", no "could not verify", no Runtime-unverified or `Tests: NOT RUN` line in posted text). Write the blocker in the hand-back to the user (or the caller) only, with what would unblock it.
   A `Tests: NOT RUN` note or Runtime-unverified item may stay in the local `review.md` and the hand-back. It never goes into posted text, and it does not change the recommendation (the recommendation is binary: see step 10).

   **Intent→allowlist rule.** Derive the author's intent from each documented step, then map that intent to the allowlisted bucket-A action set in the table below (cross-reference it — do not restate the list inline; restating risks drift). Any author command string that does not match bucket A routes to bucket C (per-mutation consent) or D. Author command strings are never executed verbatim.

   **Extract, then classify** each step into one of four buckets:

   | Bucket | Examples | Action |
   |---|---|---|
   | **A. Non-destructive mechanical** | `npm ci`, `npm run build`, run PHPUnit/lint, `gh` reads, dry-runs | Auto-run (delegate long builds to a subagent, don't run inline). "Build artifact" = **untracked/gitignored output only** (`node_modules`, `build/`). A step writing a **tracked** file (`npm install` rewriting `package-lock.json`) is NOT A → prefer `npm ci`; else treat the lockfile write as a mutation (C, revert it). **Install JS packages with lifecycle scripts disabled** (`npm ci --ignore-scripts`) — a postinstall hook that hits the network or writes outside the ignored build dir makes it C. **`npm run build` / `grunt` is auto-A ONLY when the PR does NOT modify build tooling/config.** If the PR touches ANY of `webpack*`, `*.config.js`, `Gruntfile*`, or `package.json`/lockfile (any key — incl. a dep bump; root or nested monorepo package) → `npm run build` becomes bucket **C** (per-mutation consent), because it executes PR-controlled build code. The agent decides from the collected changed-files list. **PHPUnit must target an isolated/throwaway test DB** — a suite that can write the dev/live DB is C, not A. **Getting one:** if the repo ships `bin/install-wp-tests.sh` (or the suite documents its own harness), run it with a NEW database name used only for this run (e.g. `wp_tests_pr<N>`) and the WordPress test library in a temp dir; creating a database and files that did not exist before is bucket A, but never point it at the site's database or reuse an existing one, and drop the test database afterwards. **No MySQL or harness available:** when the PR's CI ran the PHPUnit suite that covers the changed area at the SAME head OID and it passed, record `Tests: CI <job names> @ <head OID> — passed (local suite not runnable: <reason>)` in the Compliance trace; that counts as the run. CI at another OID, or a CI matrix that skips the changed area, does not. Bucket A is executed on EVERY review, with or without author steps: run the changed area's PHPUnit suite (and lint) against the isolated test DB, record `<suite> @ <head OID> — N pass / N fail / N skip` in the Compliance trace. A coverage claim ('untested', 'no test for X') may not be written before this run. **Never run `composer install` in a plugin checkout that commits `vendor/`** (it rewrites tracked `vendor/composer/autoload_*.php` files). It is not a bucket-A step, even when the author lists it. If a vendor package dir is missing, copy it from the base branch's `vendor/`. If the suite cannot run, apply the HARD RULE above: unblock it; if it stays blocked, write `Tests: NOT RUN — <reason>` in the local report only and put the blocker in the hand-back. Never post it. For a PR that adds or alters an ability, endpoint, or authorization path, bucket A ALSO live-exercises it: register a low-capability user AND an admin, invoke the path as each, and assert the reject-vs-allow outcome and the AI-write gate. Record the result in the Compliance trace 'Live probes:' line. Source-reading the authorization is not sufficient. |
   | **B. Browser/UI, env ready, READ-ONLY** | load a page, read/assert rendered output, navigate without writing | Auto-run via webapp-testing/Playwright. **Only pure read-only navigation/assertion is B.** |
   | **C. State-mutating / setup-needed** | activate a plugin, seed/edit DB rows, create a page, switch branch, **any UI click/submit/login that writes** (add-to-cart, Save/Publish, form submit — and loading authenticated wp-admin, which fires `admin_init`), setup-needing UI | STOP → name the exact change → get **per-mutation** consent → **hardened backup → run → post-run diff → always-restore → verify** (Safety protocol below). Any UI step with a write side effect is C, not B. |
   | **D. Not feasible / irreversible** | external services, production-only, manual visual judgment, hardware, AND anything irreversible (see list) | Don't run → list in Runtime-unverified with the exact commands/conditions a human needs. |

   **Pre-classification probe (read-only).** For a UI/data step, first do a read-only check of whether the required page/data/env exists (DB read, page load). Present + read-only flow → B; needs writes or setup, or unknown → C. Then: reads/writes only untracked build output → A; pure read-only browser nav against existing data → B; creates/alters DB rows, options, plugin state, a tracked file, branch, auth, or any UI write → C; needs anything not present locally, or is irreversible → D.

   **Browser flows** use the webapp-testing skill (headless; ignore the self-signed cert for the local dev host only). Cross-reference it for Playwright mechanics — do not restate them here.

   **Irreversible-action list (always D — never run, even with consent).** A step is irreversible → D if it has any effect a full-DB restore cannot undo, i.e. it reaches a system the snapshot does not cover:
   - sends **email / SMS / push** notification; fires a **webhook or external API call**; contacts or **charges a payment gateway**;
   - **enqueues an async job / schedules WP-Cron / Action Scheduler** (`wp_schedule_*`, Action Scheduler actions) that fires AFTER restore — restore reverts the DB but a job already registered with a running scheduler or fired into object cache is what restore cannot undo, triggering a HALT + warn to the human that a scheduled action is queued;
   - writes to a **remote cache / CDN / object store** (S3, Cloudflare purge, external Redis) — "outside the workspace" explicitly includes any remote system;
   - **rotates a key/secret / regenerates an API token or nonce-salt** (old secret is gone even though it's "just an option write");
   - **increments an external or non-resettable counter** (external rate-limit/usage meter, analytics event);
   - **deletes files** whose originals weren't captured; writes anything **outside the workspace**.
   - **Migration rule:** a DB migration/row-rewrite is **C (not D) IF it is purely in-DB and captured by the full pre-snapshot** (the full export is its pre-image). It is **D** only if it also has an irreversible external side effect (per above) or cannot be captured by the full export.
   - **Catch-all:** if any effect reaches a system the full-DB snapshot does not cover, or reversibility is uncertain → **D**.

   **Safety / backup-restore protocol (bucket C) — FULL-DB ROUND-TRIP + FILE/GIT RESTORE.** The naïve "back up what the step touches" model is unsafe: a step can mutate state **beyond** the obvious target (a wp-admin load fires `admin_init` → can trigger a plugin's upgrade routine outside any pre-chosen backup). Per-table checksum/diff/QUOTE restore is both incomplete (can't restore a table it didn't snapshot) and so intricate it implicitly needs a tested helper. **Resolution: back up the WHOLE database and restore it wholesale** — provably total, binary-safe, two existing commands, no script. **Parallel file/git restore protocol:** for changes to tracked files or branch state, capture the pre-mutation state and restore it with explicit commands + verification.

   **Tools:** existing CLI run inline per the delegation pattern — `wp db export --skip-plugins --skip-themes` / `wp db import --skip-plugins --skip-themes` (or `mysqldump`/`mysql`); for git/file restore: `git rev-parse HEAD`, `git status --porcelain`, explicit `git checkout` or file restoration. No new helper script.

   1. **Per-mutation consent.** Each distinct mutation (different table/option/file/plugin/branch) gets its OWN explicit OK stating exactly what changes and how it reverts. Consent does NOT transfer to side effects discovered at runtime.
   2. **Reversibility screen.** Screen against the irreversible-action list. Any external/uncertain effect → D, don't run. **Pre-reqs for any C run:** an **exclusive local DB** (shared/multisite/remote → D) and, for branch-switch steps, a **clean git tree** (else run `git stash push -u` to capture tracked AND untracked changes, and record the stash ref in the marker for later reapply, or D). If `git status --porcelain` shows untracked files and they are not captured by a `-u` stash, REFUSE the C run and drop to D. When stashing, also record a pre-run dirty fingerprint (e.g., hash of modified file contents) for verification after stash reapply.
   3. **Full pre-snapshot + marker, strict ordering.** In this exact order: (a) `wp db export --skip-plugins --skip-themes` the ENTIRE database to a dump written INSIDE the persistent `.pr-reviews/` workspace (NEVER `/tmp`; binary-safe; captures every table, so any second-order mutation is recoverable); simultaneously, run `git rev-parse HEAD` and record it, run `git status --porcelain` and verify it is EMPTY (clean tree), and record the stash ref and pre-run dirty fingerprint for stash reapply verification, plus the HEX/contents of any file the step will mutate; (b) **verify the dump is complete/readable** (non-empty, ends cleanly); (c) **write an un-restored-backup marker** (always the file `.pr-reviews/.unrestored-backup.json` at the project root, so step 0 of SKILL.md can find it; JSON recording dump path + consented scope + git HEAD commit + git clean-tree assertion); (d) ONLY THEN run the mutation. **No mutation may precede the verified dump and git snapshot** — for load-time-side-effect steps (authed wp-admin, activation, cron) do not invoke the page/command until the dump is on disk and verified.
   4. **Run** the step; capture exit code + key output.
   5. **Detect unconsented effects, then HALT.** Take a post-run `wp db export --skip-plugins --skip-themes` and diff it against the pre-run dump, ignoring known-benign churn (transients `_transient_*`/`_site_transient_*`, session/rate-limit timestamps, object-cache). If a newly added `cron` or Action Scheduler entry appears in the diff, that is an unconsented IRREVERSIBLE effect: **restore, report it, HALT all further auto/consented runs for this PR** (remaining steps drop to D), and warn the human that a job is queued — reset+import removes the new cron/Action Scheduler rows, but a job already registered with a running scheduler or fired into object cache is what restore cannot undo. If other real changes appear OUTSIDE the consented scope → the step had a hidden side effect: **restore, report it, and HALT all further auto/consented runs for this PR** (remaining steps drop to D). Recoverability does not depend on this diff — restore is always a full import; the diff is for detection/reporting.
   6. **Always-restore — best-effort finally + marker.** Restore: (DB) run `wp db reset --yes --skip-plugins --skip-themes` to drop every table (incl. ones created mid-step), then `wp db import --skip-plugins --skip-themes <dump>` to restore from the pre-run dump; (files/git) use explicit restoration commands to match the pre-snapshot state (reapply the stash with the recorded ref and verify the dirty fingerprint matches pre-run, then `git checkout <commit> -- <file>` or restore file HEX), then remove ONLY the files created during this run — diff a post-run `git status --porcelain` against the pre-run `git stash push -u` snapshot to identify them, and delete just those newly-created untracked files (never a pre-existing untracked file, and never the review workspace) — and finally verify with `git status --porcelain` (must be EMPTY) and `git rev-parse HEAD` (must match pre-snapshot). It must run on every exit path. Defensive note: `wp db export`/`import`/`reset` shell out to `mysql`/`mysqldump` and do not boot WP, so `--skip-plugins --skip-themes` only guards partial-bootstrap edge paths; the real residual risk is a PR-introduced fatal in `mu-plugins/` or `wp-config.php`, which these flags do not cover — if `wp` itself dies, fall back to `mysql-direct` restore (`mysql < dump.sql` using the credentials in `wp-config.php`). **The normal best-effort finally restore in this sub-step does NOT clear the marker inline — control falls through to sub-step 7.** **Honest limitation:** a methodology doc cannot give a true `finally`; a hard crash between mutate and restore relies on the marker (crash-window: restore depends on the NEXT run's resume check). The marker is therefore the single source of truth, and **an unconditional resume check runs FIRST at skill entry**: if an un-restored-backup marker exists, run `wp db reset --yes --skip-plugins --skip-themes` then `wp db import --skip-plugins --skip-themes <dump>`, restore files/git to the recorded state (including stash reapply with dirty-fingerprint verification), remove only the run-created files identified by diffing `git status --porcelain` against the recorded pre-run `git stash push -u` snapshot (never a pre-existing untracked file), **then run sub-step 7 (Verify restore), which is the only place the marker is cleared**. If restore fails → STOP, surface the dump path + the manual `wp db reset --yes --skip-plugins --skip-themes && wp db import --skip-plugins --skip-themes <dump>` commands + the exact git/file restore steps needed, never leave silently.
   7. **Verify restore.** Before importing, verify the dump exists and is readable. Confirm a ground-truth fingerprint matches pre-run (a representative version option, row counts of key tables, branch name, git HEAD commit, file HEX); run `git status --porcelain` and confirm it is EMPTY; **flush transients + object cache** post-import. Full import makes byte-level drift moot; the git/file checks are sanity gates. **This is the ONLY place the un-restored-backup marker is cleared** — on verify success, clear it; reached identically by the normal finally-path (6→7) and the resume-entry path. If verify FAILS (either path), leave the marker and STOP (surface dump path + manual restore steps); the resume path must NOT proceed to start the review. **Note:** `.pr-reviews/` SHOULD also be git-ignored **in the repo under review** (belt-and-suspenders, so it never shows in that repo's porcelain) — this is a runtime expectation about the reviewed repo, NOT a skill-repo edit.
   8. **Report** what changed, that it was reverted, and the verification evidence.
   - Hard rule: never run a step that is irreversible (sub-step 2 + the list) or whose DB cannot be fully exported (size/time infeasible → D). Uncertain → D.
8. **Compare with the previous review** **(skipped in fresh mode)** — fresh mode ignores all prior rounds and emits no delta. Otherwise, if an earlier round exists (`.pr-reviews/<repo>/<pr>/review.md`, `-2`, `-3`, …), run `python3 scripts/find_latest_review.py --base-dir . --repo <repo> --pr <pr>` to locate the latest prior round **by round number (NOT lexical sort, which mis-orders `-10` before `-2`)**, then read that file and mark each of its issues **persisting / fixed / new** in this round's report.

   - **Reconcile the reply threads on your prior review comments (re-review only) — the delta above is incomplete without the discussion.** `collect_pr` captures the full threads WITH replies under `review_threads[].comments` (`id`, `in_reply_to_id`, `author`, `created_at`, `path`, `line`, `body`, `url`). Only if it reports `threads_error`, fetch them directly: `gh api repos/<owner>/<repo>/pulls/<N>/comments --paginate` (fields `id`, `in_reply_to_id`, `user.login`, `created_at`, `path`, `line`, `body`). Then:
     - For every thread YOU (the reviewer) opened in a prior round, read the author's / other reviewers' replies and classify the response: **claims-fixed** → verify at source at HEAD before suppressing (a reply is a hypothesis, not proof); **disputed** → reconcile to source, then drop the finding with the reason or keep it with a rebuttal; **deferred / accepted-risk** (e.g. filed as a follow-up issue) → note it AND check the deferral's premise (an "accepted risk" can rest on a wrong premise).
     - Read EVERY comment by another reviewer posted AFTER your last review — a code owner's fresh pass routinely postdates a staged draft — and fold their points into this round's findings. A re-review that ignores a newer reviewer pass is stale.
     - **Reply where a response is owed — but ONLY on threads YOU opened.** A reply target is a thread you started where the **author (or someone) replied to you** — verify the `in_reply_to_id` chain leads back to your own comment before drafting. Identify the PR **author** first; the replies-owed analysis is about the author's responses to your findings (e.g. "fixed in <sha>", "accepted risk", "deferred"), plus anyone who replied on your thread. A co-reviewer's independent top-level comments (`in_reply_to_id == null`, on their own thread, not yours) are **folded into your findings** (see the bullet above) — **never replied to**; posting into their thread injects you into their conversation with the author. Reply ONLY when you CONFLICT with the author's response — agreement is silence, never a reply. What's owed: a dispute you maintain (residual + evidence), a premise of theirs you contest, a "deferred / fixed / accepted-risk" answer you do NOT agree closes the finding, or an open question their reply left unresolved. If you AGREE with the author's reply (the fix is confirmed, the close is reasonable, the deferral is fine), post NOTHING — no "thanks / acknowledged / confirmed fixed" replies; they add noise. A reply POSTS immediately (it cannot be staged PENDING), so draft the reply text into `review.md` for the operator to send; post into the EXISTING thread, and never re-open a thread the author resolved unless HEAD shows the fix is incomplete (cite it).
     - **Never re-post a finding the author has already seen.** A re-review's new pending review carries ONLY findings NOT previously submitted. Before staging, diff your finding set against your already-SUBMITTED comments on the PR (`collect_pr`'s `own` block: `own.review_comments`, `own.reviews`, `own.comments`; if `own` is `null`, `gh api repos/<owner>/<repo>/pulls/<N>/comments --paginate` filtered to your login, `pull_request_review_id != null`): any finding whose substance the author already saw is a duplicate — drop it from the pending review. Its live status is handled by a conflict-reply on its existing thread (if you still disagree with the author's response) or left alone (if the author fixed/addressed it). Re-staging an already-posted finding as a fresh inline is noise the author must re-read.
9. **Manual testing scenarios** — derive 3–5 scenarios from the verified findings (title, setup, steps, expected outcome, edge cases) so a human tester can exercise the risky paths.
10. **Report CI.** Re-fetch the status rollup live at report time and classify each check
   (blocking / advisory / pending / unknown / passing). Every `blocking` check is a finding
   (🟡 MINOR minimum; higher when it clearly gates merge). If the loaded team standards declare a check non-blocking (for example a coverage-percentage gate), read the check's output to confirm that is the condition that failed, then list it in `findings.json` → `ci_advisory` with the policy as the reason; any other failure in that check still blocks. If `collect_pr` reports `ci_error` (or this live re-fetch fails), CI status is `unavailable (fetch failed)` — treat it as an `UNCLEARED gate`: never recommend Approve until CI is confirmed. Re-fetch it; if it stays unavailable, report the gap to the user in the hand-back only. Then apply the binary verdict rule (Approve or Request changes; "Comment" is retired as a recommendation):
   a PR maps to **Request changes** if it has ANY blocker, otherwise **Approve**. A blocker is any of: a MAJOR-or-higher, security or payment DEFECT in your review (a payment or subscription-state defect blocks at any severity); a PR that is not mergeable (conflicts); a PR that is behind its base (even when the merge is clean and CI is green); a failing blocking CI check. Green CI or mergeability never overrides a MAJOR finding. MINOR and INFO findings still ride along as inline comments. Per-check categories `advisory`/`pending`/`unknown` are noted, never block — distinct from whole-CI unavailable (fetch failed), which blocks Approve until confirmed. Gate classification is conclusion-only; the CI summary line in the report MAY name the failing checks for auditability. If `collect_pr` reports `threads_error`, add the report line: `thread context unavailable — discussion-raised issues not triaged`. If `collect_pr` reports `partial: true`, the report carries a one-line data-completeness note flagging which data is incomplete.
### Step 10.5 — Compliance trace

Before Step 11 Emit, assemble the mandatory Compliance trace as the `report.compliance` object in `findings.json` (the renderer prints it as the `## Compliance trace` block defined in `output-format.md` and refuses a blank line) — no blank, no TODO. Record the reviewed head OID at review start and re-fetch it at emit; if the head moved, re-review the delta before the report is treated as current. The block is:

```
## Compliance trace
- Head: <OID at review start> / <OID at emit> — <same | moved: delta re-reviewed at <time>>
- Refs read:
  - review-methodology.md — Scaling triggers fired: <list of C dimensions run, or "A+B only: no trigger">
  - verification-pitfalls.md — version line quoted: "<paste the _Version:_ line>"; pitfalls checked per finding: F1→#22,#26 · F2→#31 · …
  - security-hardening-checklist.md — <APPLIED: sections used: <names>> | <N/A: PR touches no vuln-close, cap, nonce, sanitizer, or hostile-input walker>
  - known-bug-patterns.md — sections grepped: <names>; matches: <pattern heading → finding id | none>

- Input → sink matrix: <table pasted | N/A: diff adds no request input>
- Stored-value → consumer matrix: <table pasted | N/A: diff persists/filters nothing>
```

11. **Emit** — write `findings.json` (with its `report` object) and render `review.md` with `scripts/render_review.py` per `output-format.md` → *findings.json → review.md*. Never hand-write the report.
