# Verification Pitfalls

Distilled from verified findings across past WordPress plugin PR reviews and
patterns mined from review session transcripts. These are the documented ways
past reviews got it WRONG. Check the matching pitfall BEFORE reporting a finding.

_Version: 33 patterns · cross-ref: review-methodology.md verification-rigor._

## The 33 pitfall patterns

1. **Same-namespace resolution (PHP)** — before flagging a "missing `use` import", check the file's `namespace` declaration: unqualified class names resolve against the current namespace first. (Example: `Importer::can_import()` flagged CRITICAL; both classes lived in the same `MyPlugin\Import` namespace.)
2. **Outer-layer enforcement** — before flagging "missing auth/validation/license check" in a handler or service, check routers, middleware, endpoint config files, hooks, and parent callers; enforcement often lives upstream. (Example: an endpoint config file declaring the route's auth requirement, enforced by the router, not the service.)
3. **Magic getters / property aliases** — before flagging a "non-existent property", check `__get()`/`__call()` on the class and its base classes. (Example: `$order->ID` aliased to `id` by the model base class's `__get()`.)
4. **Documented intent** — read the docblock/comments around the flagged code AND any test exercising it; behavior that looks like a bug may be explicitly intended and asserted. (Example: "legacy meta preservation" flagged as data loss; the docblock and a test specify exactly that behavior.)
5. **The test already exists** — before flagging "missing test/boundary coverage", grep the test suite for the function name and READ the matching tests fully. (Example: the exact `== IP_LIMIT` boundary test existed.)
6. **Branch conflation** — trace which control-flow branch the flagged line actually executes in; the "failure case" may be impossible in that branch. (Example: selector flagged for input fields inside a branch that only runs for selects.)
7. **Adjacent documentation missed** — before flagging "missing JSDoc/PHPDoc", look DIRECTLY ABOVE the cited line. (Example: complete JSDoc 8 lines above the citation.)
8. **Project convention, not a flaw** — before flagging naming/structure, search for sibling files following the same pattern; 3+ matches = established convention, judge against it. (Example: test class `Compat` matched 8+ existing single-word test classes.)
9. **Build-tool scope** — before flagging build config overlap/gaps, identify which toolchain builds which assets; repos often run separate legacy + modern pipelines. (Example: webpack built legacy scripts only; blocks had their own toolchain.)
10. **Framework lifecycle APIs** — before flagging WordPress block/hook lifecycle issues, check the framework's compat mechanisms (`deprecated` save handlers, hook priorities). (Example: `deprecated save: () => null` prevented the claimed editor validation errors; CRITICAL→INFO.)
11. **grep-as-data-flow** — a grep returning 0 results does NOT prove code is unused or safe to delete. Before any "unused / safe to remove" claim, search dynamic references too (string-built action names, CSS class usage, filtered values) AND trace consumers (REST fields, JS stores, UI). (Example: "hook unused" claims missed string-built action types.)
12. **Comparative claim without reading both sides** — any "X does less than Y", "can be null here", or "no check for Z" finding must cite BOTH code paths plus a guard search of callers. Never assert a comparison you only read half of.
13. **Equivalence asserted from memory** — "CSS token X = hex Y", "@since/min version is N": resolve the actual variables/header file and cite file:line. Memory of token values and version numbers is unreliable.
14. **Skip/exit-code green accepted as pass** — a test run isn't green because it exited 0. Diff skipped/did-not-run counts against baseline; a broken `beforeAll` masks failures as skips; a smoke test must assert on output content, not exit code.
15. **Unexplained file waved through as "out of scope"** — every file in the diff must be explained by the PR's purpose. (Example: `package-lock.json` churn with no `package.json` change excluded from review instead of questioned.)
16. **Single-path reachability** — a function with multiple input sources (`$_GET` + block context, REST + internal call) may enforce a capability/identity check on one path and skip it on another. Before rating a guarded function "admin/editor-only," trace EVERY input path and confirm the guard on each. (Example: an "is this the editor?" helper verifies identity on its block-context path but returns a raw `$_GET` value via an early short-circuit, so anonymous front-end visitors reach the editor-only branch.)
17. **Idempotent handler ⇒ benign nonce gap** — before rating a missing-nonce/CSRF finding above INFO, read the HANDLER and confirm it mutates state. A handler that only redirects, reads, or re-derives a whitelisted value (e.g. a gateway-select handler that only appends a `payment-mode` query arg that is re-sanitized + whitelisted downstream) has no CSRF consequence. Also check whether the markup is stock framework output the PR did not introduce.
18. **Runtime hook ordering judged statically** — `do_action`/`apply_filters` order, conditional `add_filter` suppression, and `did_action()` guards depend on render order and config that static reading cannot resolve. Don't conclude such a finding either way from source — mark it runtime-unverified and emit a config-specific test. (Examples: a suppression filter that empties the only submit button in one configuration; a "missing button" claim that a runtime check disproves because a native fallback button renders.)
19. **Request-dispatched action = request-callable.** Before treating any action handler as internal, check how the hook can be fired. `admin_post_*` / `wp_ajax_*` handlers run for any logged-in user (any visitor for the `_nopriv` variants), and many plugins have a router on `init` / `admin_init` that fires `do_action( 'myplugin_' . $_REQUEST['myplugin_action'], $_GET|$_POST )` — no nonce, no capability, raw superglobal as arg 1. Every hook sharing that prefix is request-callable; a "delayed" or "known" actions list is not an allowlist unless the router enforces it. 'Only fired internally' is never a defense; a scalar type declaration fatals rather than guards. Filters are not dispatchable this way. The handler must verify its own nonce + capability. (This is an under-flag pitfall: the danger is rating a request-reachable handler "internal-only" and clearing a real hole.)
20. **Relocated request value stays attacker-controlled.** A value a handler reads from a session, transient, cache, or option is NOT trusted just because the read site is not a superglobal. If ANY request path writes that store with attacker-supplied input, the value is still attacker-controlled where it is read. Before rating a read "first-party / trusted source," trace the WRITER — find every place the session/option/cache key is set and check whether a request can reach it. (Classic miss: a request value copied into the plugin's session on one action, then read back on a later action and treated as first-party.)
21. **Guard flag set only inside the branch it gates is dead code.** A check like `if ( $this->allowed ) { … $this->allowed = true; }` — where the flag is assigned ONLY inside the block it guards — never changes the entry decision; the guard is inert. Before crediting a boolean/flag/condition as protection, find where it is WRITTEN, not just where it is read. If nothing outside the gated branch ever sets it to the passing value, the check does nothing and the code runs unprotected (or never runs at all).
22. **Sibling keys/columns reaching the same write.** When a fix server-derives ONE identifier for a DB write (e.g. binds a row id from an authenticated source instead of trusting the request), that is not "the write is now bound" until you also check whether the DATA payload forwarded to the same write can re-supply an identity/parent column under a DIFFERENT key. An `array_map()`/whitelist-merge over a request array preserves every key it doesn't explicitly strip — including `order_id`, `id`, `type`, `customer_id` — and a generic ORM/query-builder update will happily write any real column when the capability check defaults to "exists" rather than an explicit allowlist. Before crediting "the id is now server-derived" as a fix, enumerate every key of every array reaching that write and check it against the table's column list. (Example: an IDOR fix binds a child row's id server-side, closing the named vector, but a `parent_id` key in the same request array survives the write layer's column whitelist and re-parents the row onto a different parent.)
23. **Adversarially test NEW recursive/parsing code for cycles and unbounded depth.** When a PR adds a new helper that walks attacker-influenceable structured input (recursion over an unserialized array, a deserialization walk, a tree/graph traversal), don't just confirm it blocks the ONE vector the PR names — separately test the new code's own robustness: does it guard against a self-referencing/cyclic structure, and does it bound recursion depth? A hardening fix that closes an object-injection hole but adds unguarded recursion can turn a "no crash" baseline into a memory-exhaustion fatal on crafted input. (Example: a new `contains_object()` helper correctly refused disallowed classes during `unserialize()`, but recursed with no cycle/depth guard — a self-referencing serialized array caused infinite recursion and a memory-exhaustion crash the prior code did not have.)
24. **Trace the SAVE path for keys that survive an allowlist gate but skip the sanitizer.** On a settings/options save-time allowlist PR, don't stop at confirming the allowlist keeps only known keys — trace whether a key that passes the allowlist (because it belongs to another tab/section, or was already stored from before) actually reaches the type-specific sanitizer for the CURRENT section, or whether it merges into `$output` raw because the section-scoped sanitize loop never touches it. A key that survives the gate but bypasses the sanitizer can carry unescaped attacker-influenced content straight to a render sink (especially inline CSS/JS via a style/script injection helper, which is not auto-escaped). Don't conclude "sanitized" from the type-map alone; enumerate which keys reach the final merged output WITHOUT passing through a sanitizer call. (Example: a settings-hardening PR's save-time allowlist correctly rejected unknown keys, but a foreign-section/already-stored key skipped the section-scoped sanitize loop and merged raw into an option later echoed unescaped inside a `<style>` block via `wp_add_inline_style` — a stored-XSS the allowlist review missed.)
25. **A severity that hinges on an unverified runtime property must be driven live before it is capped.** When a finding's real-world exploitability depends on a runtime/config property you can't confirm by reading source alone (a cookie's SameSite attribute, a header, a feature flag's live value, whether a URL-parsing function actually fetches remotely in the target browser), do not settle severity on a plausibility argument ("probably mitigated" / "probably exploitable") — drive the specific behavior live (a live probe / browser test / harness) and rate on the confirmed result. Do not discount a finding to a lower severity because the ACTOR is gated (e.g. "only a logged-in contributor") when the finding defeats the exact security guarantee the PR exists to deliver — an actor-gated bypass of a PR's own stated hardening goal is still at least MAJOR. (Example: a CSS-sanitizer hardening PR's stated goal was "no remote fetch from CSS values" — a review lane found the `image-set()` function bypasses the `url()` block but rated it MINOR because the actor is "contributor-gated"; a live browser probe confirmed the bare-string form still fires a remote fetch, defeating the PR's own guarantee for every site visitor, which made it a blocking finding regardless of actor gating.)
26. **A "now fixed / already closed" claim carries the same evidence bar as an open one.** Before you downgrade or drop a finding because something is said to be fixed, resolved, or no longer reachable — whether the claim comes from the PR description, a commit message, a review reply, or your own earlier pass — re-trace the affected path end-to-end at HEAD and cite `file:line` for the fix. A "fixed" claim is a hypothesis until the source proves it. Trace the EDGE shapes too — malformed, array-typed, empty, or out-of-order input — because a fix that handles the named happy-path vector often still leaves an alternate-shape input reaching the same sink. How to check: read the current code at HEAD, follow every input shape to the sink, and confirm the guard fires on each before lowering severity.
27. **Persisted-record inconsistency is a data-integrity MAJOR — rate every impact axis and take the max.** When a change can leave stored data in a self-inconsistent state — an order line dropped while the total is not recalculated, a parent row updated without its children, a stored count that no longer matches the rows it counts — treat the data-integrity impact as at least MAJOR even when there is no security or crash angle. A single finding usually sits on several impact axes (security, data integrity, correctness, performance, UX); rate each axis and assign the finding the HIGHEST severity among them, not the first one you noticed. How to check: after any write/update path, ask which other stored fields must move together with the value being written, and whether a partial write can leave the record contradicting itself.
28. **Stateful flag: build the set/clear/read matrix across EVERY mutating path.** A flag that gates a charge, credit, or skip is safe only if every path that completes the gated action also clears it — directly, or via a shared clearer every payment path provably routes through. Before crediting "the double-charge is fixed", list setters, clearers, and readers of the flag and check each payment-collecting entry point (sync checkout, update-payment-method, each webhook, admin, cron). (Example: a payment-failure flag whose clearer has one caller, in one recovery path; payments arriving by other paths bypass it, so a later recovery inside the paid period charges again.)
29. **A nonce is not authorization; a raised-then-reverted guard is an open decision, not a closure.** Before accepting "the cross-object vector is removed", name the capability that gates the write and confirm a holder cannot supply another object's id. Run `git log -p` on the guard; if the PR raised it and then reverted it, report the revert with both hashes as an OPEN scope decision. (Example: a per-object nonce is added and the capability raised to a manage-level one, then reverted to a view-level one; a review that reads only the final diff calls the vector closed.)
30. **A declared type with no implementation is a hole; enumerate real instances of every declared type.** Reviewing a sanitization/registry pipeline for internal soundness is not enough. For each declared type or schema entry, list the REAL registered items of that type, confirm a concrete sanitizer/handler class exists for it, and trace each item to its render sink. A type present in the shape list but absent from the implementation map falls to a Fallback you must read. (Example: a `color` field type listed in the scalar-type map with no sanitizer class falls back to `sanitize_textarea_field`, and the stored value is echoed unescaped into a class attribute.)
31. **A new filter/hook contract has consumers and malformed returns; enumerate both.** When a PR adds `apply_filters()` / `do_action()` whose value reaches a render, export, query, or persisted field, list EVERY consumer of the filtered value (not only the screen the PR shows) and test a malformed return (non-array, empty, missing key) on each. A raw sink behind a "dev-only" callback is still a contract gap: rate it MINOR minimum, never INFO by default. (Example: a new list-table row filter whose export and filtered-view consumers were ignored, and whose non-array return fatals the whole screen.)
32. **"Edge" or ">N seconds" is a likelihood claim that must be measured.** Before capping a race, orphan window, or timing finding as an edge case, time or reproduce the window in the local environment (a gateway round trip, a cron interval, a webhook delay). If you cannot measure it, log it runtime-unverified with the severity-if-routine, never MINOR on a guess. (Example: an orphan window dismissed as a rare edge case that reproduces on every gateway call is MAJOR.)
33. **A coverage claim needs a suite run at the reviewed head; the head can move.** Never write "untested" or "no test covers X" before running the suite (grep is not a run, pitfall 5 is not enough). Record the head OID with the run; at emit re-fetch the head and, if it moved, re-review the delta before the report is treated as current. (Example: "untested" findings that existing tests at the reviewed head already cover, or a head that has moved on with commits addressing the findings.)

## Mandatory pre-verdict checklist

Before a review lane records ANY verdict at MAJOR or above (or an Approve on a
security/payment-touching PR), answer each of these in the report's **Compliance
trace** block (see `output-format.md`); an unanswered item means the verdict is
not ready to emit:

- **All inputs to the sink**: for every fix that binds/validates ONE value reaching
  a write/render sink, what are the OTHER values reaching the SAME sink, and are
  they equally bound/validated? (pitfall 16, 22)
- **All consumers of a stored value**: if this PR's fix writes or persists a value,
  what are ALL the places that value is later read (not just the one path under
  review)? (pitfall 20)
- **Adversarial input on new code**: if this PR adds new code that parses, walks,
  or recurses over structured/attacker-influenceable input, what happens on a
  cyclic, malformed, or maximally-deep input? (pitfall 23)
- **Runtime-dependent severity**: does this finding's severity depend on a runtime
  property (cookie flag, header, live config, browser behavior) that source
  reading alone cannot confirm? If yes, has it been driven live, or is it
  explicitly logged as runtime-unverified? (pitfall 25)
- **Base-branch diff for "pre-existing" claims**: if a finding is being downgraded
  or dismissed as "pre-existing," has the exact cited line been diffed against the
  PR's actual base branch (not assumed)?
- **Flag matrix**: if the diff touches a payment/subscription state or any flag
  that gates a charge/credit/skip, is the set/clear/read matrix complete across
  every mutating path? (pitfall 28)
- **Authorization vs CSRF**: on any access-control change, which capability gates
  the write, and did the PR's own history raise then revert it? (pitfall 29)
- **Suite run at head**: has the changed area's suite run at the reviewed head
  OID, and is that OID the live head at emit? (pitfall 33)

A verdict that skips this checklist is not a completed review.

## Severity calibration (check before assigning MAJOR or CRITICAL)

Historical downgrades cluster into these themes — severity miscalibration is as
common as outright false positives:

- **Outer gate already enforces** — an upstream capability check/middleware makes the inner gap defense-in-depth, not a hole.
- **Admin-only reachability** — path only reachable by trusted roles (a shop-settings capability, editor contexts) → usually MINOR.
- **Downstream guard** — real smell, but later validation blocks hostile data → PARTIALLY VALID at lower severity.
- **Legacy/compat handler covers it** — deprecated formats already matched by existing handlers.
- **Cosmetic-only impact** — no data loss/corruption/broken flow → not MAJOR.
- **Object-cache-backed transients** — repeated `get_transient()` calls are near-free in production.
- **Functionally identical style variants** (e.g. `WP_REST_Server::CREATABLE` vs `'POST'`) → INFO.
- **First-party values are not attacker-controlled** — before rating a sanitization/XSS finding above MINOR, trace the tainted value to its origin: your own REST API responses, PHP `wp_localize_script` strings, and server constants are trusted sources. A recurring over-flag.
- **Framework provides the mechanism the PR omits** — when the framework ships a standard solution the PR skips (a Gutenberg `deprecated.migrate`, a core sanitizer, a cap helper), the omission is usually MAJOR not MINOR: it causes the silent data loss / breakage the framework was built to prevent. (Example: a lossy block deprecation with no `migrate` silently drops attributes on save; that is MAJOR, not MINOR.)
- **Actor gating / dev gating lowers likelihood, not the impact floor** — "only a contributor", "only a developer callback", "only admins" is a likelihood note. If the finding defeats the PR's own guarantee, it stays ≥ MAJOR (pitfall 25); a dev-gated raw sink introduced by a new public contract is MINOR minimum (pitfall 31).
- **Reachability dismissed on timing must be measured** — see pitfall 32.

## Base rates (for the two-pass verifier)

Historically most verified findings are confirmed, with a minority downgraded in severity and a small share of false positives. That is not a target; 100% confirmed is fine if every CRITICAL/MAJOR cites file:line evidence and ran the pitfall checklist.

**Static-only reviews have a reachability ceiling.** Security and behavioral findings that depend on runtime config or hook ordering can be neither confirmed nor refuted by reading. A static pass that finds no HIGH/CRITICAL has NOT cleared them — it has cleared only the statically-visible ones. Record what remains runtime-unverified (see `output-format.md` → Runtime-unverified) so an APPROVE is never mistaken for "fully cleared."
